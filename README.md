# Трекер калорій

Особистий щоденник калорій. Фронтенд це один файл `index.html` (без збірки), що живе на GitHub Pages:
https://oleksandrvashchishak.github.io/tracker/

Дані зберігаються в Google Таблиці «Калорії» через скрипт Google Apps Script. Застосунок працює з локальною копією в `localStorage`, а зміни у фоні відправляє в таблицю.

## Структура
| Шлях | Що це |
|---|---|
| `index.html` | увесь застосунок (HTML, CSS, JS). Те, що в `main`, те й публікується |
| `apps-script/Code.gs` | серверний код. Розгортається вручну в Apps Script, у репозиторії з заглушками замість токена й ID таблиці |
| `tools/harness.js` | макет Google: запускає справжній `Code.gs` з підробленими сервісами й віддає застосунок |
| `tools/test-server.js` | перевірки протоколу бекенду на макеті |
| `tools/check.js` | перевірка синтаксису скрипта в `index.html` |

## Як перевіряти зміни
```
node tools/check.js            # синтаксис
node tools/harness.js          # макет на http://localhost:8767/ (окремий термінал)
node tools/test-server.js      # протокол бекенду
```
Інтерфейс перевіряйте в браузері на `http://localhost:8767/`. Макет підміняє адресу бекенду й токен, тож **справжня таблиця не зачіпається**.

## Як працює синхронізація (коротко)
- Кожне збереження порівнюється з останнім відомим станом, різниця (лише `set` і `del` по рядках) йде в чергу й відправляється пакетами.
- Сервер веде версію таблиці (`rev`). Пристрій, що відстав, отримує `stale`, підтягує нове й накладає на нього свої зміни.
- Пристрій нічого не застосовує з таблиці, якщо вона виглядає як втрата даних (`looksLost`).
- Сервер відхиляє заміну вкладки без `force` і видалення понад 20% рядків, робить резервні копії в Drive й веде вкладку «Журнал».

## Правила, які не можна порушувати
1. **Ніколи не тестуйте на справжній таблиці.** Лише макет `tools/harness.js`. Не вписуйте справжню адресу `/exec` чи токен у тести, скрипти й повідомлення комітів.
2. **Не повертайте автоматичні `replace` («замінити все») у синхронізацію.** Це знімок стану, який може лишитися в черзі й пізніше затерти таблицю. Заміна лише вручну з підтвердженням (`force`).
3. **Не змінюйте порядок колонок** у вкладках таблиці й `TABLES` у `Code.gs`: скрипт читає їх за позицією.
4. **Скрипт розгортається лише як «New version»** у Manage deployments. «New deployment» змінює адресу, і всі пристрої втратять зв'язок.
5. **Не додавайте нових секретів у репозиторій.** Токен і адреса `/exec` у `index.html` (`DEFAULT_SYNC`) там свідомо, за рішенням власника. Нові ключі чи паролі туди не потрапляють.
6. Дані користувача не видаляти, не «чистити» й не перезаписувати без явного прохання.

## Робота кількох агентів
- Одна задача, одна гілка: `agent/<тема>`. Зміни зливаються в `main` лише після `node tools/check.js` і, якщо чіпали синхронізацію чи `Code.gs`, після `node tools/test-server.js` та перевірки сценаріїв у браузері на макеті.
- `index.html` це один великий файл. Щоб не конфліктувати, чіпайте різні ділянки (розділи розмічені коментарями `/* ---------- … ---------- */`) й робіть невеликі коміти.
- Публікація це push у `main`. Після нього GitHub Pages оновиться за 1–2 хвилини, а браузери можуть кешувати сторінку до ~10 хвилин.
- Зміни `Code.gs` треба окремо вручну вставити в Apps Script і розгорнути (див. правило 4). Скажіть власнику про це.
